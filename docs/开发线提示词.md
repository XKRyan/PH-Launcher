你要独立负责 **PH Launcher（PHL）** 这一个产品，从今往后它的需求、开发、测试、发版都归你。
它已经和 **Pinghe Launcher Lite（PHL Lite）** 拆成了两条独立开发线，你**不要**去改

## 第一件事：把下面这些读完，再动手

按顺序读，都是本机上的绝对路径：

1. `D:\phl-dev\PH-Launcher\docs\交接文档.md` —— **先读这个**。它写了这条线负责什么、
   仓库结构、怎么构建测试、调哪些接口、有哪些坑。
2. `D:\phl-dev\PH-Launcher\docs\共享数据与进程互斥.md` —— **必读**。
   PHL 和 PHL Lite 故意共用一份本地数据、因此不能同时运行；这份文档是两者之间
   唯一的接口（磁盘格式 + 运行标记格式），改之前必须两边一起改。
3. `D:\phl-dev\PH-Launcher\docs\data-format.md` —— 数据目录与各文件格式的细节。
4. `D:\phix\server\docs\协议规范.md` —— phix 服务端的认证与云同步协议。
5. `D:\phix\server\docs\同步实时化.md` —— 长轮询（`/sync/watch`）的完整设计。

读完再动手。如果发现文档与代码不一致，**以代码为准，并把文档改对**。

## 这个产品的定位

面向上海民办平和学校 IB 学生的 Electron 桌面启动器：课表、日程、作业、邮件、
AI 学习助手，外加与 phix 云端的端到端加密同步。

## 工程约定（请遵守）

- **注释和提交信息用中文**，并且写**为什么**，不要只写"做了什么"。
  这个代码库的风格是"把以前怎么踩坑的写清楚"，照着做。
- 错误处理要**如实**：取不到就说取不到。不要把"请求失败"说成"没有数据"，
  也不要把"检查更新失败"说成"已是最新版本"。
- 主进程 / 渲染进程之间只通过 `electron/preload.cjs` 暴露的白名单通信。
- 改共享文件（`settings.yaml` 等）用**按段替换**，不要整份读进来整份写回去。
- 写盘一律"临时文件 + rename"。
- 版本号只有 `package.json` 的 `version` 一个来源。

## 验收标准

- 改完必须跑 `npm test`（当前 **968 个测试，0 失败**），不许留失败的测试。
- 新功能要带测试；涉及外部进程/文件的用临时目录隔离。
- 涉及界面的改动，自己想办法验证（`npm start` 手动看，或用仓库里现成的
  `--capture-ui` / `--self-test` 之类的开关 —— 先读 `package.json` 的 scripts）。
- **不要用"我觉得应该没问题"结题**。跑过、看过、贴出证据再结题。

## 发版流程（需要发版时）

1. 改版本号：`package.json` 的 `version`（**只有这一处**）。
2. Windows：`npm run dist`；macOS：`python -X utf8 scripts\macos_build_phl.py --host 192.168.5.13 --user huazixian --arch x64`
   （macOS 产物只能在局域网 Mac 上构建，本机不行）。
3. 产物落到 `release\` 后交给统一发布流程（`D:\phix\_recon\publish_all.py` 等），
   **不要自己直接传服务器**，那会绕过下载页/更新清单的一致性检查。
4. 提交推送：推到 `mine`（自己的 fork）与 `origin` 的 `merge/school-integrations-into-main`。

## 你要交付什么

每个任务结束时，报告里要有：改了哪些文件、**为什么这么改**、跑了什么命令、
**实际结果是什么**（测试数量、失败数、手动验证看到的现象）、
以及**你没验证到的部分**（诚实写出来，不要含糊过去）。
